中心になるのは6つのサービスだよ。流れを図にするとこうなる。

プロジェクトとリージョンはどうなっていましたか？

上

プロジェクトは ai-product-446711、リージョンは東京の asia-northeast1。気をつけたいのは、このプロジェクトに別サービスの ai-product も同居していたこと。これが第9章の片付けで大きく効いてくる。

上

第2章terraform/cloud-run.tf

Cloud Run：「サーバーを持たない」ことの損と得

Cloud Run と普通のサーバー（VM）は何が違うんですか？

上

VM はアクセスがなくても24時間動いていて、その分お金がかかる。Cloud Run はリクエストが来たときにコンテナを起動して、来なくなったら止める。正確には、次のリクエストに備えてアイドルのインスタンスを最大15分ほど残してから止めるんだ。

最大2台は少なすぎませんか？

上

このアプリにはちょうどいいんだ。Terraform でデプロイした Cloud Run は、1台あたり vCPU × 80 件のリクエストを同時に処理できる。ここは 1 vCPU だから、2台で同時に最大160件。個人の学習サービスには十分だよ。

落とし穴ただし、これを請求額の上限だと思うのは間違い。上限を超えたリクエストはしばらく（10秒以上）待たされて、それでも空きがなければ 429 エラーになる。だから Gemini の課金が一気に膨らむのを抑えるブレーキにはなるけど、処理できる範囲のアクセスが続けば請求は積み上がっていく。総額を抑えたいなら、予算アラートや API のクォータを組み合わせる。

0台から起動するときは遅くなりませんか？

上

なるよ。これがコールドスタート。その対策として次の2行を入れている。

startup_probe と liveness_probe がどちらも /api/health を見ているのはなぜですか？

上

同じ URL でも目的が違う。

プローブいつ見るか失敗したら
startup_probe起動直後成功するまでリクエストを流さない。期限（failure_threshold × period_seconds）内に成功しなければコンテナを停止する
liveness_probestartup の成功後、30秒ごと失敗が続くと固まったとみなし、コンテナを SIGKILL で停止する。新しいインスタンスに置き換わる

cloud-run.tf:160 の ignore_changes で image を無視しているのはなぜですか？

上

ここはよく出題されるポイントだね。イメージを更新するのは GitHub Actions の仕事。もし Terraform もイメージを管理していたら、terraform apply した瞬間に tfvars に書かれた古いタグへ戻ってしまう。どの属性をどのツールが管理するかを分けるための宣言なんだ。

cloud-run.tf:183 の allUsers は、誰でもアクセスできるということですか？

上

そう、インターネット上の全員に公開している。Web サイトだから公開するのは当然で、API の保護はアプリ側（Supabase Auth）でやる。インフラでは全部開けて、アプリで認証するという分担だ。これが第6章の伏線になる。

Insight

  • max_instance_count はスケールの設定であると同時にコストのブレーキです。同時に処理できる量を抑えるので、従量課金の外部 API（ここでは Gemini）への請求が一気に膨らむのを防げます。ただし請求総額の上限ではないので、予算アラートと組み合わせます。
  • ignore_changes は「Terraform で全部を管理する」考え方への例外です。CI/CD が頻繁に書き換える属性は、Terraform から外して管理者を1つに絞るのが定石です。

第3章terraform/cloud-run.tfweb/Dockerfile

Artifact Registry と Dockerfile

Artifact Registry は、プライベートな Docker Hub のようなものですか？

上

その理解で合っている。イメージの住所はこういう形になる。

asia-northeast1-docker.pkg.devリージョンのレジストリ
/
ai-product-446711プロジェクト
/
kabu-news-aiリポジトリ
/
appイメージ名
:
<コミットSHA>タグ

タグに latest を使わないんですか？

上

variables.tf:33 で、Terraform に渡すタグとしての latest をバリデーションで禁止している。CI は SHA と一緒に latest タグも付けているけど、デプロイと Terraform で指定するのは SHA だけだ。

誤解しやすいのが「latest だと元に戻せない」という話。Cloud Run はデプロイした時点でタグをイメージのダイジェスト（中身のハッシュ）に置き換えて、リビジョンに固定する。だから前のリビジョンに戻すことはできる。本当の問題は Terraform 側にある。latest という文字列は変わらないから、新しいイメージを push しても plan に差分が出ず、デプロイのきっかけにならない。それにタグ名を見ても、どのコミットかが分からない。SHA ならコードとイメージが1対1で対応する。

web/Dockerfile は3段構成になっていますね。

上

マルチステージビルドだね。

  1. deps：依存パッケージだけをインストールする。package.json と pnpm-lock.yaml が変わらなければキャッシュが効く
  2. builder：ソースをコピーして pnpm build を実行する
  3. runner：Next.js の standalone 出力だけをコピーし、非 root の nextjs ユーザーで起動する

最終イメージにソースも開発用パッケージも入らないから小さくなって、転送も起動も速くなる。

上級者として、何か反省点はありますか？

上

改善点片付けのときに分かったんだけど、Artifact Registry に 6.0 GiB もたまっていた。コミットごとにイメージを push していて、古いものを消すクリーンアップポリシーを設定していなかったからだ。ストレージは少しずつ課金されるから、作るときに cleanup_policies で「最新 N 個だけ残す」と決めておくべきだった。

第4章terraform/secrets.tf

Secret Manager：秘密の渡し方は3種類ある

Supabase のキーはどうやってアプリに渡していたんですか？

上

Cloud Run が起動するときに Secret Manager から読み込んで、環境変数に入れている。

secrets.tf には値が書かれていませんが？

上

わざとだよ。Terraform が作るのは入れ物（Secret）だけで、値は gcloud secrets versions add で手で登録する。値を Terraform に書くと state ファイルに平文で残るからね。

IAM の付与が Secret ごとに4つも並んでいて、冗長に見えます。

上

「Secret Manager 全体を読める」権限をまとめて渡すこともできる。でもそうすると、後から追加した Secret までアプリが読めてしまう。1つずつ付けておけば、新しい Secret はデフォルトで読めない状態になる。冗長さと引き換えに安全を買っているんだ。

version = "latest" なら、値を更新すればすぐに反映されますか？

上

落とし穴されない。環境変数として渡す Secret は、インスタンスが起動したときに読み込まれる。だから、すでに動いているインスタンスは古い値のまま。確実に反映させたいなら、新しいリビジョンをデプロイする必要がある。

改善点この性質があるので、Google は環境変数で使う Secret には latest ではなくバージョンを固定することを推奨している。常に最新の値を使いたいなら、Secret をファイルとしてマウントする方法がある。こちらは読むたびに Secret Manager から最新の値を取ってくる。

秘密の渡し方が3種類あるというのは？

上

いつ必要になるか、誰に見えてよいかで経路を分けている。

種類例渡し方
実行時の秘密SUPABASE_SERVICE_ROLE_KEYSecret Manager → Cloud Run の環境変数
ビルド時の秘密同じキー（ビルド中に使う分）BuildKit の --mount=type=secret。そのコマンドの実行中だけ見え、イメージに残らない
ビルド時の公開値NEXT_PUBLIC_*Docker の ARG。ブラウザに配られる値なので秘密ではない

第5章terraform/iam.tf

IAM とサービスアカウント：「誰が」「何を」「どこで」

サービスアカウントは何のためにあるんですか？

上

プログラム用のアカウントだよ。このアプリには3つあって、それぞれ役割が1つずつ決まっている。

サービスアカウント使う人権限
cloud-run-appアプリ本体Vertex AI の利用、各 Secret の読み取り
api-schedulerCloud SchedulerCloud Run の呼び出しだけ
github-actions-deployGitHub Actionsイメージの push、デプロイ、cloud-run-app として振る舞う権限

ここで上級者向けの観点を1つ。IAM はどこに付けるか（スコープ）も設計の一部なんだ。

ロール付与した単位
aiplatform.userプロジェクト（iam.tf:13）
secretmanager.secretAccessorSecret 1つ
artifactregistry.writerリポジトリ1つ
run.invoker / run.developerCloud Run サービス1つ

プロジェクト単位で付けるのが楽だけど、同居プロジェクトでそれをやると ai-product のリソースまで触れてしまう。リソース単位で付けておいたおかげで、2つのサービスの境界が IAM で守られていたんだ。

workload-identity.tf:91 の serviceAccountUser は何ですか？

上

「この SA として振る舞ってよい」という権限（actAs）だよ。GitHub Actions が「cloud-run-app として動く Cloud Run」をデプロイするには、自分が cloud-run-app として振る舞えなければならない。これがないと、弱い SA が強い SA を指定したサービスをデプロイして権限を奪うことができてしまう。それを防ぐための関所なんだ。

Vertex AI の API キーはどこにあるんですか？

上

ないんだ。コードは vertexai: true とプロジェクトIDを渡しているだけ。

認証は ADC（Application Default Credentials） が環境に合わせて自動で選ぶ。

  • Cloud Run 上：メタデータサーバーが cloud-run-app のトークンを渡す
  • ローカル：gcloud auth application-default login で登録した開発者本人の認証情報を使う

コードは同じで、認証情報を環境が決める。漏れる鍵がそもそも存在しないのが一番強い。iam.tf:30 の serviceAccountTokenCreator は、開発者がローカルで cloud-run-app になりすまして、本番と同じ権限で試すためのものだよ。

Search Console と GA4 も ADC ですか？

上

落とし穴そう。ただしこの2つは GCP の IAM の外側に権限がある。それぞれの管理画面で SA のメールアドレスをユーザーとして追加しないと、IAM をいくら付けても 403 が返ってくる。

Insight

  • この構成（kabu-news-ai の Terraform と CI）は、SA キー（JSON ファイル）を1つも使っていません。Cloud Run は ADC、CI は WIF、ローカルは gcloud となりすましを使っています。漏れる鍵を持たないことは、とても効果的な漏洩対策です。
  • 同じプロジェクトに複数のサービスがあるときは、ロールをリソース単位で付けることがサービス間の境界になります。第9章で安全に削除できたのも、この分離があったからです。

第6章terraform/cloud-scheduler.tf

Cloud Scheduler と OIDC：決まった時刻に叩く仕組みを守る

毎朝9時の予測トレーニング生成はどう動いていたんですか？

上

Cloud Scheduler が9時に /api/cron/generate-prediction へ POST を送るだけだよ。time_zone = "Asia/Tokyo" を忘れると UTC で解釈されて、9時間ずれるから注意。

でも Cloud Run は allUsers で公開されていましたよね。誰でもその URL を叩けるのでは？

上

鋭いね。叩けてしまうと、他人がこちらの Gemini 課金を勝手に発生させられる。だから oidc_token で、Scheduler は「私は api-scheduler です」という Google が署名した身分証を添えて送る。そしてアプリ側で検証する。

  1. Google の正しい署名があるか → 偽造トークンを弾く
  2. email が api-scheduler@… 本人か → 他人の正規トークンを弾く

iam.tf:19 の scheduler_invoker で Cloud Run の呼び出しを許可しているのは、Scheduler 用の門番ではないんですか？

上

落とし穴ここが上級者向けのポイント。allUsers にすでに run.invoker があるから、このバインディングは今は門番として働いていない。コメントには「これがないと呼び出せない」と書いてあるけど、公開サービスである限りそうはならない。本当の門番はアプリの verifySchedulerToken だ。このバインディングが意味を持つのは、Cloud Run を非公開にしたときだね。

ただし、非公開にするならアプリ側の検証も変える必要がある。認証が必要なサービスでは、Cloud Run が IAM でトークンを検証したあと、使い回しを防ぐために署名を取り除いてからコンテナに渡す。すると今の verifyIdToken は、署名の検証で必ず失敗する。非公開にするなら、検証は IAM に任せて、アプリはトークンの中身（email）を読むだけ、という形に変えることになる。

検証コードに改善できるところはありますか？

上

改善点ある。verifyIdToken({ idToken }) に audience を渡していないから、トークンの宛先（aud）を確認していない。Terraform では audience = Cloud Run の URI と設定しているんだから、アプリ側でも照合するのが正しい形だ。持ち主が api-scheduler に限られているので実害は小さいけど、多層防御としては穴になっている。

ジョブがすべて paused = true になっていますね。

上

落とし穴サービス終了のときに Gemini の課金を止めたんだ。gcloud scheduler jobs pause で止めて、コードにも paused = true を書いた。ここは誤解しやすいところで、paused は Optional＋Computed という種類の属性だから、コードに書かなくても apply で ENABLED に戻ることはない。コードに書かれていない属性は、実際の値をそのまま受け入れるんだ。

それでも書いておく意味は、ジョブが作り直されたときにも停止状態で作られること。.tf が残っているから、誰かが apply すればジョブは新しく作られうる。コードに書かない属性がどう扱われるかはプロバイダのスキーマで決まるから、「手で変えたら必ず巻き戻る」と思い込まずに、属性ごとに確かめるのが大事だよ。

第7章terraform/workload-identity.tf.github/workflows/deploy.yml

Workload Identity Federation：鍵を渡さない CI/CD

GitHub Actions はどうやって GCP にログインしていたんですか？

上

昔は SA キーの JSON を GitHub Secrets に入れていた。でも漏れたらそれで終わりの合鍵を外に預けることになる。WIF では、合鍵の代わりにその都度発行される身分証を使う。

  1. GitHub が「このジョブは Takeshi-005/kabu-news-ai で動いています」という OIDC トークンを発行する（deploy.yml:41 の id-token: write が許可）
  2. Google の Security Token Service が、Pool（受付）と Provider（GitHub を信頼する設定）に従ってトークンを検証し、短期のトークンに交換する
  3. 検証に通ると github-actions-deploy SA として動けるようになる

attribute_condition がないとどうなりますか？

上

他のリポジトリのトークンでも、受付（プールでのトークン交換）を通れてしまう。この構成では SA 側のバインディングでも principalSet://…/attribute.repository/Takeshi-005/kabu-news-ai と絞っているから、それだけで SA を借りられるわけではない。つまりこの1行は、二重の鍵の1つ目だ。GitHub のトークンの発行元は全リポジトリで共通だから、Google のドキュメントもこういう場合は attribute condition を必ず使うよう求めている。

改善点さらに言うと、リポジトリの名前で絞るより assertion.repository_id（数値ID）で絞るほうが強い。名前は削除や改名のあと他人に取り直される可能性があるけど、ID は再利用されないからね。

PR でもビルドは走るんですか？

上

走るけど push: ${{ github.event_name == 'push' }} だから push はしない。マージしてからビルドが壊れていると気づく、という事故を防ぐためだ。terraform/ を変えた PR では terraform-plan.yml が plan の結果を PR にコメントする。apply の前に差分をレビューするという流れだね。

その plan はちゃんと動いていたんですか？

上

落とし穴それが、2026-07-02 以降はずっと失敗していたんだ。キャンセルされた plan がロックを残して、それ以降の PR ではロックを取れずに終わっていた。それでも結果は success と表示された。terraform plan … | tee plan.txt とパイプすると、パイプ全体の終了コードは最後の tee の 0 になるからね。GitHub Actions の既定のシェルは pipefail を有効にしない（shell: bash と明示すると有効になる）。緑のチェックは、失敗していないことの証明にはならないんだ。

第8章terraform/backend.tf

Terraform の state

state はどこに置いてあったんですか？

上

GCS バケット ai-product-446711-terraform-state だよ。backend.tf は中身が空で、外から渡す partial configuration にしている。文書では prefix を kabu-news-ai にする決まりだったんだけど、実際の state はバケット直下（prefix なし）にあった。

決まりと実際がずれたのはどうしてですか？

上

落とし穴2026-02-19 に、ローカルで prefix を付けずに init したからなんだ。prefix は省略できる設定で、付け忘れてもエラーにならず、バケット直下が使われる。以降の apply も、停止のときの state rm も直下に書かれて、prefix 側には2月の古い state が残り続けた。その古い state にはシークレットが6件、平文で入っていたから、2026-09-24 に削除したよ。

部分設定は便利だけど、渡し忘れた値は黙って既定値になる。state を触る前に、.terraform/terraform.tfstate に記録された backend の設定を確かめる習慣をつけよう。

state が消えたらどうなりますか？

上

Terraform は「自分が何を作ったか」を忘れる。実際のリソースは残っているのに、apply すると全部新しく作ろうとして衝突する。だからローカルではなく、ロックがかかる GCS に置くんだ。

第9章docs/shutdown/SHUTDOWN_CHECKLIST.md

片付け編：同居プロジェクトの安全な撤収

削除は terraform destroy で一発ですか？

上

このプロジェクトでは禁止。同居している ai-product の資産まで巻き込む恐れがあるからだ。実際の手順はこうだった。

順やったことポイント
1Scheduler を停止課金を止める。元に戻せる操作を最初に
2GSC 16ヶ月分と Supabase のデータを退避取り返しがつかないものから先に確保
3money-nav.com を Firebase Hosting へ移すDNS-01 チャレンジで先に証明書を取り、停止時間ゼロで切り替え
4名前を指定してリソースを個別に削除保護リストとの部分一致でガードする
5terraform state rm で26件を state から外すAPI 有効化の9件は ai-product が使っているので残す
6リポジトリをアーカイブ.tf が残っているので、apply すると作り直しが始まる（イメージがないので Cloud Run の作成で失敗し、途中で止まる）。read-only 化が最後の安全装置

削除の順番にも決まりがあるんですか？

上

落とし穴ある。

  • ドメインマッピング → Cloud Run の順。逆にすると、マッピングだけが行き先のない状態で残ってしまう（孤児化）
  • IAM バインディング → SA の順。逆にすると、ポリシーに deleted:serviceAccount:…?uid=… という残骸が残る。GCP が最大60日で自動的に消すけど、先にバインディングを外せば、その場できれいになる

それから、紛らわしい名前が並んでいた。WIF プールの my-pool（別リポジトリ用で保護）と github-actions-pool（削除対象）、プロバイダの github-actions-oidc（保護）と github-provider（削除対象）。名前のガードだけでは依存関係の見落としは防げないから、削除の前に「その SA を実際に使っているのは誰か」を gcloud run services describe で確認した。

DNS ゾーンは消さなかったんですか？

上

消していない。google-site-verification の TXT レコードが Search Console の所有権を支えているし、ドメインは次のプロダクトで使い回す予定だからね。作るより消すほうが、依存関係の理解を問われる。これがこの章の教訓だ。

Insight

  • 片付けは「元に戻せる操作 → 取り返しのつかないデータの確保 → 取り返しのつかない削除」の順に進めるのが原則です。Scheduler の停止が最初、state rm とアーカイブが最後だったのはそのためです。
  • Terraform の .tf と state、そして実際のリソースは、それぞれ別の状態を持ちます。「state から外した ≠ 実体を消した」「実体を消した ≠ .tf から消えた」を区別できると、Terraform の理解が一段深まります。

理解度チェック

答えはすべて本文にあります。自分の言葉で答えてから解答例を開いてください。

  1. /api/cron/generate-prediction に攻撃者が直接 POST したら、どこで・なぜ弾かれるでしょうか？（allUsers と scheduler_invoker の関係を踏まえて）

    解答例を見る

    Cloud Run は allUsers に run.invoker を与えているので、リクエストはインフラ層では止まらずアプリまで届きます。scheduler_invoker はここでは効いていません。

    弾くのはルートハンドラ冒頭の verifySchedulerToken で、401 Unauthorized が返ります。Bearer トークンがなければその場で不合格、偽造トークンは Google 署名の検証で失敗、別の SA の正規トークンは email が api-scheduler@… と一致せず失敗します。

  2. cloud-run.tf から ignore_changes の image を消して terraform apply すると、何が起きるでしょうか？

    解答例を見る

    GitHub Actions がデプロイした最新イメージ（コミットSHA）と、tfvars の app_image_tag（古い値）の差分を Terraform が検出し、plan に image の変更が出ます。

    そのまま apply すると古いイメージで新しいリビジョンが作られ、本番が過去のバージョンに巻き戻ります。

  3. github-actions-deploy から serviceAccountUser を外すと、デプロイのどの段階で失敗するでしょうか？そして、それはなぜ必要な制約なのでしょうか？

    解答例を見る

    イメージのビルドと push は artifactregistry.writer で通ります。失敗するのは deploy ジョブの Cloud Run 更新で、iam.serviceAccounts.actAs の権限不足エラーになります。

    run.developer だけでサービスを作れると、強い権限の SA を指定したサービスをデプロイし、その SA の権限で任意のコードを動かせてしまいます（権限昇格）。actAs を要求することで、「その SA として振る舞ってよい人」だけがその SA を使うサービスを作れるようになります。
